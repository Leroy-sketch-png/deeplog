# Analyst Feedback Lifecycle Schema

This document outlines the structured schema for capturing ground-truth SOC analyst decisions on anomalies generated by the DeepLog Behavioral Engine.

## Objective
Before any automated unlearning or adaptive model updates (like LSTM iteration) can be justified, we require a mathematically queryable ground-truth collection mechanism. Analysts triage alerts in the SOC, and this system logs their final verdicts back into the `data/feedback.sqlite` database.

## SQLite Schema: `feedback`

| Column | Type | Description |
| :--- | :--- | :--- |
| `id` | INTEGER (PK) | Auto-incrementing primary key |
| `timestamp` | TEXT | ISO 8601 UTC timestamp of when the feedback was submitted |
| `alert_id` | TEXT | The exact CorrelationId (Track A) or Caller ID/Session Timestamp (Track B) |
| `track` | TEXT | `A` (Lifecycle) or `B` (Session) |
| `decision` | TEXT | Must be one of the exact Enum values below |
| `reason` | TEXT | A 1-sentence plain-text reason provided by the analyst |
| `analyst_id` | TEXT | Corporate ID of the SOC analyst |

## Allowed Decisions (Enum)
1. **`BENIGN_FALSE_POSITIVE`**: The alert mathematically triggered correctly against priors, but the behavior is operationally normal (e.g., a scheduled deployment, a known script change).
2. **`CONFIRMED_ANOMALY`**: The alert correctly flagged malicious or dangerously broken behavior.
3. **`UNREVIEWED`**: Pushed into the queue but timed out or lacked context to make a determination.

## Intake Mechanism (CLI)
The feedback system is hard-wired into the project CLI. Analysts or automated SOAR playbooks can submit feedback directly:

```bash
python -m deeplog submit-feedback \
  --track A \
  --id "0b8882fb-0603-4d9f-9a5b-caced38a7142" \
  --decision BENIGN_FALSE_POSITIVE \
  --reason "Approved cross-tenant migration." \
  --analyst "SOC_Tier2_Jane"
```

*Note: Automated unlearning is NOT active. This data serves strictly as the foundational requirement for future research into dynamic suppression.*
